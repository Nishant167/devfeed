# Threat Model

> **State: Current Design.** No code is deployed, so no threat below has been exercised or tested, and no mitigation listed as "planned" below is actually running. This documents realistic threats to the target system and whether a mitigation is Current Design, Planned, or a genuine gap with no mitigation defined at all.

| Threat | Impact | Mitigation (design intent, not implemented) | Status | Remaining risk |
|---|---|---|---|---|
| GitHub API credential (PAT) exposure | Rate-limit abuse against the project's quota, or account-level actions if the token has broader scope than needed | Token is designed to be configuration, injected at runtime, never hard-coded; never committed | Current Design (`.gitignore` exclusion is Implemented; the token-handling code it protects doesn't exist yet) | No secret-scanning tooling is configured yet in CI (none exists); no documented token-scope minimization policy (e.g., read-only PAT) is specified in `DEVFEED.md` |
| Malicious or adversarial repository metadata (e.g., a crafted description/README designed to break parsing or later, prompt-inject an AI analysis step) | Ingestion crash or corrupted data; future AI-analysis prompt injection once Stage 7 exists | Defensive parsing designed to tolerate missing/null/unexpected fields; repository code is never executed, at any stage, regardless of confidence in the analysis pipeline | Current Design — no ingestion code exists yet to verify this holds | AI-analysis-specific prompt-injection defenses aren't designed yet, because the AI analysis feature (Stage 7) doesn't exist yet — this is a real forward risk to track when that stage begins |
| API abuse (scraping, excessive request volume) | Degraded feed latency for other users, inflated hosting cost | API-level rate limiting is explicitly named as a Stage 4 addition tied to authentication | Planned (Stage 4) — no mitigation of any kind exists between now and then | Between now and Stage 4, there is no documented rate-limiting control on the specified public API at all; this is an accepted gap for the Stage 2 timeframe, not an oversight, but it is a real exposure once the API is actually deployed |
| Injection (SQL injection, unvalidated input reaching the database) | Data corruption or unauthorized data access | Request validation is designed to run through Pydantic schemas at the API boundary; SQLAlchemy (ORM) is the specified data-access layer, which normally parameterizes queries by default | Current Design — no implementation exists yet to verify this holds in practice | This is a design intention, not a tested control; SQLAlchemy's default parameterization is a property of the library, not something DevFeed's own code has demonstrated yet |
| Unauthorized access to internal data | Exposure of raw ingestion payloads, quality scores, or (once they exist) user data | No authentication exists at Stage 2, and there's also no user-specific data to protect yet beyond an anonymous, privilege-free `session_id` | Implemented fact (no auth, by design, per [`authentication-authorization.md`](./authentication-authorization.md)) | Once Stage 4 accounts exist, this threat becomes materially more serious and needs a real authorization design — not yet specified beyond "arrives alongside auth" (Planned, Stage 4) |
| Denial of service against the ingestion job or API | Ingestion failure, feed unavailability | Ingestion designed to back off with jitter on `403`/`5xx` from GitHub and retry; a single repository's ingestion failure designed to never abort the whole batch (`sync_status: error` and skip) | Current Design — no ingestion code exists yet | No DoS protection is designed for the DevFeed-facing API itself (e.g., no documented request throttling, no CDN/WAF) — this is a genuine gap, not just an unimplemented design; PostgreSQL is explicitly the one dependency the system can't degrade around — a DB outage is a full outage |
| Dependency vulnerabilities | Compromise via a vulnerable third-party package | `SECURITY.md` commits to keeping dependencies current and flagging known vulnerabilities in pinned versions | Current Design (policy stated; no dependencies exist yet to apply it to, and no scanning tool is configured) | No automated scanning (Dependabot, `pip-audit`, `npm audit` in CI) is configured yet — there's no CI at all yet, let alone a security-scanning step within it |

## What this threat model deliberately does not cover

Threats specific to features that don't exist yet — AI codebase execution risks beyond the "never execute repository code" rule, social-layer abuse (spam, harassment) ahead of the Stage 10 social layer, and payment/fraud risk (no monetization exists or is planned in the current build) — are out of scope here because inventing detailed mitigations for unbuilt features would misrepresent the project's actual security posture.
